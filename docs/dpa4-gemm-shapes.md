数据来源：`docs/artifacts/dpa4_air_cpu.fx.txt`（整模型 FX 图）与
`dpa4_air_so2_conv.fx.txt`（单个 SO(2) 卷积子图），两者都是 `print_readable()` 的产物，
形状是**符号化**的。

## 四个族（按输出形状）

| 族 | 形状（符号） | 真实 B3000 规模（N=3000, 9 槽） | K | 说明 |
| --- | --- | --- | --- | --- |
| **readout 瘦长** | `[1, 152, 48] × [1, 48, 64·N·9]` | N = **1 728 000** | 48 | 单条最大：`2·152·48·1.728M ≈ 25 GFLOP` |
| **per-edge gated 投影** | `[1, E, K] × [1, K, 640]` / `[1, K, 192]` | M = E，N = 640 / 192 | **64** | 每个卷积层 8 次（640/192 交替） |
| **per-edge rank-K 收缩** | `[E, 10, 64] ← [E, 10, K]·[E, K, 64]` | batch = E，M = 10/16，N = 64 | **64** | 小 batch 多次（每层 3 次） |
| **atom 侧投影** | `[16, N·9, 64]`、`[16, N·9, 192]`、`[16, N·9, 1152]` | batch 16，M = N·9 = 27000，N = 64–1152 | **64** | 每层 4–6 次 |

## 对我们的 dense kernel 意味着什么

1. **K 很小**：几乎全是 `K = 48 / 64`，个别 128–256。按 `kKT=8`，那是 **6–8 个 k-step**。
   我们为 4096³（512 个 k-step）调的流水、预取深度、乒乓 stage，在 8 个 step 里只能摊到很少的
   循环迭代上。
2. **epilogue 占比大**：分块写回要 4 次屏障 + 8 KiB LDS 往返，而正文只有 8 个 k-step。
   所以对这批形状，`DPA4_DENSE_CCHUNK=0`（整块写回、少 3 次屏障）很可能更快——与 4096³ 的结论相反。
3. **M 轴很大、N 轴很小**：M = E（10^4–10^5 量级）或 N·9 = 27000，N = 64–640。
   这正是"高瘦 GEMM"，`128×64` 的 tile 在 N 方向只覆盖 1–2 个块，**网格全靠 M 撑**，
   所以 tile 选择应由 M 与 K 决定，而不是只看 M×N。
4. **两条巨长的 readout** 是唯一 `K=48` 但 `N=1.7M` 的形状：那里 N 方向切块、M 只有 152 →
   **M 方向严重不足**（152/128 = 2 块高），需要 N 方向并行 + 可能 split-K。
