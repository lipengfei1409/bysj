# 前向 + 反向的算子时间占比（仅模型内部）

本文回答两个问题：**模型自己（`nn.Module: ModelWrapper_0` 内部）在设备上花的时间怎么分布**，
以及**已经实现的融合分别吃掉了其中的哪几行**。工具：`tests/deepmd/profile/op_time_share.py`。

```bash
python tests/deepmd/profile/op_time_share.py dpa4_inference_trace.json \
    --module 'nn.Module: ModelWrapper_0' --top 30 --json /tmp/share.json
```

## 1. 口径

| 项 | 值 |
| --- | --- |
| trace | `dpa4_inference_trace.json`（3000 原子 / 181838 边，`pt` 后端，`n_atten_head=1`） |
| 设备 kernel | 2614 次 launch，合计 **1218.58 ms** |
| 模型作用域 | `nn.Module: ModelWrapper_0`，CPU 侧时间窗 254.6 ms |
| **落在作用域内的 kernel** | **2614 / 2614（100%），1218.58 ms** |
| 前向 | 943 次 launch，**436.21 ms（35.8%）** |
| 反向 | 1573 次 launch，**780.38 ms（64.0%）** |

两点必须说清楚：

1. **作用域过滤在本 trace 上是恒等变换**——整张图（含力/维里的 autograd 反向）都在
   `ModelWrapper_0` 的调用里入队，作用域外没有模型算子。之所以过滤仍是必需的：这条判据在
   其它 trace（多步 LAMMPS、带邻居表构建的 run）上会剔除掉非模型工作，不能省。
2. **过滤键必须是 launch 时间，不是设备时间**。整张图在 254 ms 内全部入队，设备要花
   1218 ms 才排空；按设备时间戳过滤只会命中前向的 604 个 kernel（223 ms），把反向整段丢掉。

前向/反向的切分沿用 `scan_fusion_patterns.py` 的区间标注：
前向 = `sezm.py(1470): forward_with_edges`，反向 = `transform_output.py(214): edge_energy_deriv`，
两者之外只有 2.0 ms。

`gemm` 28.2% 是唯一有算力可挖的一块。

| 融合 | 接缝 | 命中的 trace 行 | 池子 | 覆盖率 | 预期收益 |

## 5. 对旧估算的两处修正

1. **B3 的"95 ms 池"是错的**。旧估算把 `index_add_ [1,E,3,64]`（32.7 ms）、
   `_index_put_impl_ [E,4,64]`（13.9 ms）、`gather/index` 若干行算进了力装配。这些行的 index
   长度分别是 9 / 4 / 10，是 **gate 与 SO(2)/SO(3) 槽位 gather 的反向**（C1/C7 的地盘），
   不是力/维里散射。真正的力装配是 `index_add [3000,3]`（dst/src 各一次）、
   `index_add [3000,9]`（源端维里）、一次 `(E,3,1)×(E,1,3)` 外积，**合计 1.7 ms**。
   `force_assembly` 算子本身 5.53×（1.006 → 0.182 ms）是真实的，但端到端最多 −1.5 ms。
2. **B1 的 −15…−25 ms 偏乐观**。前向 E→N 散射实测 11.2 ms（3 次，3.7 ms/次）；
   0.745 GB 在 630 GB/s 下是 1.2 ms，因此收益上限是 −10 ms，不是 −25 ms。
